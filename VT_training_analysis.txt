  趋势分析：
    ❌ Step 0 的 498.7 是加载 iter5 checkpoint 的初始 eval（iter5 本身的运气好值）
    ❌ 此后持续恶化：498.7 → 442.4，下降 56 步（-11.3%）
    ❌ 80M 步（2×常规训练量）也无法恢复到 493 基线
    ❌ 呈明显下降趋势，未见任何恢复迹象

  变化原因：
    1. ※Value Function Mismatch※：
       soft_contact 引入新的 reward 通道 → 旧 value function 无法正确估值
       → PPO 优势估计 (A = R_actual - V_predicted) 偏差大
       → 梯度方向错误 → 策略偏离最优解
    2. ※奖励信号冲突※：
       soft_contact 鼓励 "保持力在安全区间 [0.1N, 2.5N]"
       force_overload 惩罚 ">2.8N"
       hold_position 奖励位置不动
       → 三者在自由空间的梯度方向不一致 → 策略收到矛盾信号
    3. ※修改过多的同老教训※：
       同时新增 soft_contact + 修改 force_overload 权重和形式
       → 永远无法确定单一失败原因
    4. 80M 步仍下降 → 这不是 "训练不够" 的问题，而是 reward 设计有害

  │   iter5: 同参数续训 → 493 步（饱和）                                 │
  │                                                                        │
  │ 成功因素：力 obs 让策略从 "盲推" 变为 "触觉闭环"                     │
  │ 饱和原因：PPO 在当前 MLP + reward 下的优化极限                        │
  └──────────────────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────────────────────┐
  │ 阶段 C：VT-stage iter6~12（突破尝试全部失败）   2026-04-09 ~ 04-10    │
  │                                                                        │
  │ 策略：同 B 阶段 + 各种改动尝试                                        │
  │ 最佳：无一超越 iter5 的 493                                            │
  │                                                                        │
  │ 尝试及失败原因：                                                       │
  │   iter6:  unroll↑ updates↑ → PPO 超参失调 → -10 步                  │
  │   iter7:  reward 权重↑ → value mismatch → 恢复到 494                 │
  │   iter8:  iter7 续训 → 持续恶化至 460 → 方案 A 彻底失败              │
  │   iter9:  γ→0.995 + soft_contact → 双重失败 → 487                   │
  │   iter10: ramp 1.5→1s → 任务变难 → 487                              │
  │   iter11: 80M 步加长 → 仍退化至 442 → soft_contact 有害              │
  │   iter12: noise 0.3→0.15 → obs 分布偏移 → 465                       │
  │                                                                        │
  │ 核心教训：从 checkpoint 恢复时，任何改变 reward/obs 分布的修改         │
  │ 都会导致 value function mismatch，需要大量步数恢复且通常无法超越原值  │
  └──────────────────────────────────────────────────────────────────────────┘

                  四、RMA 师生蒸馏架构（已设计，未投入训练）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  代码位置：sim_rl/rma_reference.py（PyTorch 参考实现，214K 参数）

  设计目的：
    - 当前 PPO+MLP 在 sim 中已饱和于 493 步
    - RMA 架构旨在支持 Sim2Real 迁移，而非直接提升 sim 性能
    - Teacher 在 sim 中获得精确力信号训练编码器
    - Student 用真实硬件的历史触觉序列近似同一 latent → 部署到硬件

  架构：
    Teacher:  精确力(15D) → MLP(128,64) → z_t(8D)
    Student:  历史(50帧×17D) → TCN(32,64,64) → pool → z_hat(8D)
    Policy:   (proprio 17D + z_t/z_hat 8D) → MLP(512,256,128) → action(6D)
    蒸馏:     L = MSE(z_hat, z_t.detach())

  状态：设计完成、代码验证通过，等待决策是否投入训练。

                          五、结论与建议
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  已验证的成功因素（按收益排序）：
    1. γ = 0.97 → 0.99        : +35 步（iter4，最大单次突破）
    2. 力加入 obs 状态空间     : V 425 → VT 493（+68 步跨阶段提升）
    3. LR 退火 (3e-4→5e-5)    : +16 步（iter3）
    4. force_contact 启用      : V 90 → V 263（+173 步，V-stage 内突破）
    5. ramp 课程学习            : V 263 → V 388（+125 步，V-stage 稳定化）

  已验证的失败/无效因素：
    1. reward 权重放大          : value mismatch → 退化
    2. 新增 reward 通道         : soft_contact → 持续恶化
    3. γ = 0.99 → 0.995        : 无效
    4. unroll/updates 增大      : PPO 超参敏感 → 退化
    5. noise 减半               : obs 分布偏移 → 退化
    6. ramp 时间缩短            : 任务变难 → 退化

  当前 493 步平台期的可能突破方向：
    a) 从零训练 200M+ 步（避免 checkpoint value mismatch）
    b) 增加观测维度（滑移速度、接触法向量、力变化率）
    c) 更大网络（1024,512,256 或引入 attention）
    d) 改用 SAC / REDQ 等 off-policy 算法（样本效率更高）
    e) 接受 493 为 sim 天花板 → 转向 Sim2Real + RMA 部署
